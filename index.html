Technical report · November 2026

Penoodle: Local-First Annotation of the Web with End-to-End Encrypted Sync and Zero-Knowledge Sharing

The Penoodle Project · github.com/penoodle

Abstract

Web annotation tools usually make a server the source of truth: notes live in the cloud, need an account, and are readable by whoever runs the service. Penoodle is a browser extension for annotating web pages and PDFs (sticky notes, text highlights, freehand drawing, whiteboards and diagrams) built the other way round. Every feature that can run on the device runs signed out and offline. An optional account adds services that need a server: sync across devices, share links and live co-viewing. These are designed so the server stores only ciphertext and never learns page URLs, annotation text or keys. This report describes the architecture, the data model built on hybrid logical clocks and durable deletion markers, the key hierarchy for sync, the format of encrypted share links, and the testing and accessibility practice used to keep the system correct.

Keywords: local-first software, web annotation, end-to-end encryption, hybrid logical clocks, browser extensions, accessibility

1Introduction

Reading on the web is active work: people highlight, write in the margin, sketch over diagrams and come back weeks later expecting the marks to still be there. Pages, however, are not documents a reader owns. They change layout, re-render on every visit and are often served from origins the reader cannot write to. An annotation layer therefore has to live beside the page: it must find its place again on each visit, persist somewhere the reader controls, and, when shared, travel without exposing more than intended.

Most existing tools solve persistence by uploading every annotation to a service. That choice brings convenience across devices, but it also makes the account a prerequisite, turns the vendor into a reader of everything annotated, and leaves the work unusable offline. The local-first approach [1] suggests another order of priorities: the device holds the primary copy, the network is an optimisation, and collaboration must not cost the user ownership or privacy.

Penoodle applies that approach to web annotation. The contributions described here are:

  • a local-first feature boundary: everything that runs on the device works with no account and no network, and only features that need a server (sync, sharing, live sessions) depend on signing in;
  • a per-annotation revision scheme using hybrid logical clocks [2] with deletion markers kept long enough for an offline device to learn about deletions, which makes merging deterministic without a central sequencer;
  • end-to-end encrypted sync in which the server stores opaque records keyed by an HMAC of the page URL, and cannot read, re-target or forge records;
  • share links whose key lives only in the URL fragment, so a recipient with no account and no extension can read shared annotations while the server holds only ciphertext.

2Design goals

  1. Offline by default. Drawing, notes, highlights, screenshots, export, the PDF viewer, whiteboards and diagrams work signed out and without a network. Work made before signing in moves into the account at sign-in instead of being lost.
  2. The server is not trusted with content. Where data must cross the network, it is encrypted on the device with keys the server never receives.
  3. Nothing silently disappears. Every change gets a revision; deleted items go to a trash and can be restored, and earlier versions of a page's annotations can be brought back.
  4. The page is not disturbed. The in-page interface is isolated from the host page's styles and scripts, and the page's own content is never rewritten to store annotations.
  5. Usable by everyone. Every surface meets WCAG 2.1 AA [7] in light and dark themes, and is operable by keyboard and screen reader.

3System architecture

Penoodle is a Manifest V3 browser extension for Chromium-based browsers, plus a small set of optional services (Figure 1).

Content script. On each page, the content script mounts the interface (toolbar, annotation panel, sticky notes, drawing canvas) inside a closed shadow root. This shields it from the page's CSS and keeps page scripts away from its DOM. It loads the page's annotations from local storage, renders them and saves edits automatically. Text highlights are anchored with text-quote selectors in the style of the W3C Web Annotation model [6], so they reattach after layout changes. Inside the extension, components communicate over an event bus and typed runtime messages with timeouts.

Extension pages. A whiteboard and PDF workspace, a diagram designer, a reader, a library of all annotated pages, and pages for sync settings and invitations. They use the same storage layer as the content script.

Service worker. It owns authentication state, runs the sync engine and relays every server call. Concentrating network access in one component gives a single place to enforce which account a request belongs to, refresh tokens one at a time, and refuse messages from unexpected senders.

Services. ExtServer is an HTTP API for accounts, plans, sync records and shares. EdgeServer, ProjectionServer and EventServer carry live sessions and plan-change notifications over WebSockets and Redis. A MonitorServer aggregates health checks.

4Data model on the device

4.1Storage and ownership

Annotations for a page are stored as one encrypted entry keyed by an owner scope and the SHA-256 of the normalised page URL. Normalisation (dropping fragments and tracking parameters, for example) makes a page and its trivial variants share one entry. The owner scope is local when signed out and the account's key when signed in. At sign-in, local work is migrated into the account scope, so creating an account never costs the user what they made offline. Large objects such as PDFs and diagram sessions live in IndexedDB.

All writes go through a single store that performs read-modify-write under a per-page lock. No caller may load an entry, change it and write it back on its own, because two tabs doing that concurrently would lose one of the edits.

4.2Revisions with hybrid logical clocks

Each annotation carries a revision issued by a hybrid logical clock (HLC) [2]. A revision is a fixed-width string

MMMMMMMMMMMMM-CCCC-DDDDDDDDXXXX
13-digit ms   counter  device id (8) + context id (4)

so revisions compare in time order by plain string comparison. tick() returns a revision greater than any the clock has issued or observed, and observe(rev) moves the clock past a remote revision. A device whose wall clock runs behind therefore never issues a revision lower than one it has already seen. The device id is 8 random base32 characters, created once per browser profile. The context id separates two tabs on the same device that write in the same millisecond. The store stamps revisions centrally: an annotation gets a new revision only when its content actually changed, compared as stable JSON without the revision field.

4.3Trash, deletion markers and history

Whenever an annotation id leaves a page's list, by an explicit delete, a whole-canvas save, a restore or an incoming sync, the store moves it to an encrypted trash with its own new revision. The deleted content is kept for 30 days so the user can restore it. The marker (id and revision) is kept for 180 days. That window is how long a device can stay offline and still learn of the deletion, instead of resurrecting the item on its next sync. The store also keeps the last ten snapshots of each page, and restoring one first saves the current state as a snapshot, so a restore can itself be undone.

With revisions and markers, merging is a per-item rule with no central coordinator: for each id, the highest revision wins, whether it is an edit or a deletion. The rule is commutative, associative and idempotent, so devices converge whatever order they receive changes in.

5End-to-end encrypted sync

5.1Key hierarchy

The first device to turn sync on creates a 32-byte data-encryption key (DEK). HKDF-SHA256 [3] derives two subkeys from it: an AES-GCM-256 key [4] for record contents and an HMAC-SHA256 key for page identifiers. The DEK is wrapped twice:

  • by a key derived from the user's passphrase (PBKDF2-SHA256 [5], 600,000 iterations, random salt, at least 10 characters after Unicode NFC normalisation);
  • by a key derived from a recovery code of 26 base32 characters (130 bits), shown once and confirmed by retyping its last group.

The server stores only the keyset: the two salts, iteration counts and wrapped copies of the DEK, plus a key identifier. On an unlocked device, the subkeys are kept as non-extractable WebCrypto keys in IndexedDB. The DEK itself is never stored, and its buffers are zeroed after use. Changing the passphrase or recovery code is a compare-and-swap on the keyset, so two devices cannot overwrite each other's change.

5.2Records

A sync record is one annotation or one deletion marker:

{ pageKey, entryId, rev, deleted, ciphertext }
pageKey    = base64url(HMAC(pageSubkey, normalisedUrl))[0..32]
ciphertext = iv(12) ‖ AES-GCM(encSubkey, payload,
             AAD = pageKey | entryId | rev | deleted)

The server sees neither URLs nor content. It sees opaque page keys, ids, revisions and ciphertext. Because the metadata is bound into the AEAD's additional data, the server cannot change a record's revision, flip it between edit and deletion, or move it to another item without decryption failing. After decrypting, the client also recomputes the page key from the URL inside the payload and rejects a mismatch, so a record cannot be replayed onto a different page. A record that fails any check is skipped and counted in the sync status, never applied.

5.3Engine

The sync engine runs in the service worker when an account is signed in, the plan allows sync and this device holds unlocked keys. It is triggered at start-up, every two minutes, ten seconds after local changes settle, and on demand. One sync runs at a time, and errors back off from one to thirty minutes. Each run pulls records after a server-assigned cursor, decrypts them, and applies them page by page with the merge rule of §4.3 under that page's lock. It then pushes every item whose revision differs from what was last acknowledged. Revisions that arrived by pull are recorded as acknowledged, so they are never echoed back. Open tabs showing a changed page are told to reload its annotations.

The API client is bound to one account. If the stored session turns out to belong to another account (after a sign-out and sign-in in another window, say), requests fail before they are sent, so one account's data can never be pushed into another's.

6Zero-knowledge share links

A share link has the form

https://<host>/share/<shareId>#k=<key>

The extension generates the share id and a fresh 32-byte key, and encrypts the page's shareable annotations (with an optional note from the sharer) using AES-GCM, with penoodle-share-v1|<shareId> as additional data. It then uploads only the ciphertext under that id. Browsers do not send the fragment to servers, so the key never reaches the server; viewer pages also send Referrer-Policy: no-referrer. A recipient without the extension opens the link in any browser, where a static viewer decrypts in the page. A recipient with the extension sees the annotations as a read-only layer on the live page and can add them to their own, merged rather than replaced. The same dependency-free WebCrypto module produces and opens links in the extension and the web viewer, so the two cannot drift apart.

7Live projection

For teaching and review, a host can project a page or whiteboard to receivers in real time. The service worker keeps one WebSocket to an EdgeServer gateway. Rooms are managed by a ProjectionServer, and room membership and server registration live in Redis, so gateways can scale horizontally and a receiver can join through any of them. The host decides whether receivers may draw, and that permission applies to people who join later as well. Live sessions are one of the few features that depend on an account, because they need a server to relay strokes between people.

8Sessions and authentication

Accounts use short-lived signed access tokens bound to a per-device session, plus a refresh token of the form <sessionId>.<secret> that is rotated on every use. Presenting an already-used refresh token is treated as theft and revokes the session. Only the service worker refreshes, with a single request in flight. Web pages that complete a sign-in hand the token to the extension once and do not keep it. Password-reset and email-verification tokens travel only in URL fragments, are single-use and are stored hashed. Server pages are served with a Content Security Policy that forbids inline script and style. Audit logs never record tokens, keys, ciphertext, passwords or reset links.

9Accessibility

Every surface, including in-page UI, extension pages and server pages, is designed to WCAG 2.1 AA [7] in both light and dark themes, and the diagram designer in five canvas themes. Contrast is measured against the real backdrop, including each stop of a gradient and stacked translucent layers. Focus rings must reach 3:1 against the surface around the control. Dialogs trap focus, menus follow the WAI-ARIA patterns, status messages use live regions, and animations respect prefers-reduced-motion.

A closed shadow root introduces a problem of its own: users' text-spacing tools (user stylesheets, reading extensions) cannot reach it. Penoodle therefore offers the WCAG 1.4.12 spacing values (1.5 line height, 0.12em letter spacing and so on) as a built-in preference that applies to the in-page UI and every extension page, and tests that no text is clipped when it is on.

Accessibility is enforced the same way as functional behaviour: the end-to-end suite runs axe-core [8] together with custom checks for gradients, translucent layers, field boundaries and focus rings on every surface in both themes, so a regression fails the build. Security properties such as the server's refusal of tampered records, page-key mismatch and replayed refresh tokens are tested directly, not assumed.

11Limitations and future work

  • Metadata. The server still learns how many records an account has, their sizes, revision timestamps and when devices sync. Padding and batching could reduce this.
  • Granularity. Merging is per annotation: two concurrent edits to the same sticky note resolve to the later one. Character-level CRDTs for note text would preserve both.
  • Offline horizon. A device offline for more than 180 days may miss deletions whose markers have expired.
  • Key loss. Losing both the passphrase and the recovery code makes synced data unrecoverable from the server by design. Data already on devices is unaffected.
  • Anchoring. Text-quote anchoring can fail on pages whose text changes substantially. The annotation stays in storage rather than being deleted, but it cannot be shown in place; surfacing such annotations to the user is future work.

12Conclusion

Penoodle shows that a feature-rich annotation tool can treat the device as the home of the user's work and the server as an untrusted courier. Three mechanisms, each simple, carry most of the weight: hybrid-logical-clock revisions with long-lived deletion markers make merging deterministic; authenticated encryption with metadata bound into the additional data lets the server store and order records it cannot read or alter; and keeping share keys in the URL fragment makes sharing work without an account or the extension while the server holds only ciphertext.
